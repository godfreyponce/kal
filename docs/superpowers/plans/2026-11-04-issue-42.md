# One CI workflow + Dependabot (#42) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every pull request and every push to main runs `npm ci`, `npm audit --audit-level=high`, `vitest run` and `tsc --noEmit` in GitHub Actions, and Dependabot opens dependency update PRs.

**Architecture:** One workflow file, `.github/workflows/ci.yml`, with one job and four check steps. The live-DB test step gets `DATABASE_URL` from a repo secret and runs only when that secret exists. Without the secret (Dependabot and fork PRs get none), the step is skipped and a visible warning is printed. One `.github/dependabot.yml` turns on weekly npm version updates. The audit step fails on `main` today (1 critical, 13 high), so Task 1 fixes the dependencies first. Otherwise the new gate is red from its first run.

**Tech Stack:** GitHub Actions (`actions/checkout@v4`, `actions/setup-node@v4`, matching `pages.yml`), Node 24 (the local version, v24.14.1), npm 11, vitest 4, Next 16.

**Spec:** Issue #42 (`gh issue view 42`). It is labeled `ready-for-agent` and `red-team`. The owner typed `/run-ticket 42`, so this plan uses the normal flow. Memory says red-team issues go through `/kal-redteam`, but no such command exists in `~/.claude/commands` or the repo today. No design spec.

## Decisions (gate 1)

Planner picks, not yet confirmed by the owner:

1. **Fix the dependencies in this ticket (Task 1) so the audit step is green from its first run.** Bump `next` and `eslint-config-next` from `16.2.9` to `16.4.5` (exact pins, as today). Run `npm audit fix` without `--force`. Add `"overrides": { "zod": "^4.6.6" }` to `package.json` for the `@vercel/blob` chain. Do not downgrade `@vercel/blob`. *Alternative:* land CI alone, red, and file the dependency fixes as a new issue. A gate that is red on day one teaches everyone to ignore it, and the Next proxy bypass should ship anyway.
2. **Triggers:** `pull_request`, `push` to `main`, and `workflow_dispatch`. `workflow_dispatch` lets the owner run CI once by hand after setting the secret. `pages.yml` has the same trigger.
3. **Secret scope:** only the `npm test` step gets `DATABASE_URL`. `npm ci` runs dependency install scripts, so those scripts never see the database URL.
4. **No secret, no tests, but a visible warning.** When the secret is empty, the test step is skipped and the job prints a `::warning::`. The job stays green. Dependabot PRs and fork PRs land here. Do **not** add `DATABASE_URL` as a Dependabot secret: a Dependabot PR runs an unreviewed package version, and that code must not get a database URL. The owner runs `npm test` locally before merging a Dependabot PR.
5. **The secret's value is a Neon branch, not the live database (owner setup step, no code change).** CI and a local `npm test` in a worktree can run at the same time. Two runs that snapshot and restore the same live rows can leave test values in the real profile. Create a Neon branch named `ci` from the prod branch and use its URL for the secret. When a later ticket adds a migration, reset the `ci` branch from its parent in the Neon dashboard. *Alternative:* use the same live URL as `.env.local`, which the ticket text assumes. That works and accepts the race risk. The workflow file is the same either way.
6. **Serialize CI runs and never cancel one mid-suite:** `concurrency: { group: ci-live-db, cancel-in-progress: false }`. A cancelled vitest run can stop between a snapshot and its restore.
7. **Typecheck runs inline as `npx tsc --noEmit`.** No `typecheck` script. AGENTS.md's full check already names that command, and the ticket allows either.
8. **Dependabot:** npm only, weekly, with all updates grouped into one PR (`groups: { npm: { patterns: ["*"] } }`). One PR a week instead of one per package. The `github-actions` ecosystem is left out; the ticket asks for dependency scanning of npm.
9. **Repo settings are owner steps at accept time:** set the secret, turn on Dependabot alerts and security updates (commands in "Owner steps after accept"). The build session does not change repo settings or handle the database URL.

### Task 2: CI workflow and Dependabot config

**Files:**
- Create: `.github/workflows/ci.yml`
- Create: `.github/dependabot.yml`

**Interfaces:**
- Consumes: Task 1's green `npm audit --audit-level=high`.
- Produces: a workflow named `ci` with one job `check`, which reads repo secret `DATABASE_URL`.

- [ ] **Step 1: Write `.github/workflows/ci.yml`.** The workflow pins Decisions 2 to 7 and is short enough to give whole:

```yaml
name: ci

on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

# The suite writes live rows and restores them at the end; a cancelled run can skip the restore.
concurrency:
  group: ci-live-db
  cancel-in-progress: false

jobs:
  check:
    runs-on: ubuntu-latest
    env:
      HAS_DATABASE_URL: ${{ secrets.DATABASE_URL != '' }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm audit --audit-level=high
      - run: npx tsc --noEmit
      - name: vitest run
        if: env.HAS_DATABASE_URL == 'true'
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
        run: npm test
      - name: vitest skipped
        if: env.HAS_DATABASE_URL != 'true'
        run: echo "::warning::vitest skipped, no DATABASE_URL secret (Dependabot and fork pull requests get none). Run npm test locally before merging."
```
