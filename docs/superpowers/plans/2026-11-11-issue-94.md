# Keep the login limiter store alive (#94) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Free Upstash store `kal-login-limiter` never goes 30 days without a command, so it is not archived and new logins on Kal and star keep working.

**Architecture:** A Vercel cron job calls `GET /api/cron/keepalive` once a day. The route checks the `Authorization: Bearer <CRON_SECRET>` header before it touches anything. With a match, it runs one `INCR keepalive:kal` on the store through the existing `upstashStore()`. Without a match, it returns 401 and never calls Upstash. `proxy.ts` lets this one path through without a session, because the cron request has no cookie. The limiter stays fail closed. `lib/rate-limit.ts` does not change.

**Tech Stack:** Next 16 route handler, Vercel Cron Jobs (`vercel.json` `crons`), `@upstash/redis` through `upstashStore()`, `node:crypto` `timingSafeEqual`, Vitest.

**Spec:** Issue #94 (`gh issue view 94`). No comments, no blocker, no design spec. Read `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md` before you write the route. That doc says route handlers are not cached by default, so the route needs no `dynamic` export.

**Sources for the numbers:**
- Upstash FAQ (https://upstash.com/docs/redis/help/faq): "Free tier databases are archived after a minimum of 30 days of inactivity." "Users get several warning emails prior to this operation." The FAQ does not define activity.
- Vercel cron limits (https://vercel.com/docs/cron-jobs/usage-and-pricing): Hobby allows at most once per day, and a run can land anywhere in the scheduled hour. Delivery is best effort, with no retry.
- Upstash pricing (https://upstash.com/pricing/redis): Free is 500K commands per month. Pay as You Go is $0.20 per 100K commands, with a monthly budget cap. Over the cap, "your database will be rate limited".

## Data flow

```text
Vercel Cron, daily 10:00 UTC (new, vercel.json)
   |
   |  GET /api/cron/keepalive
   |  Authorization: Bearer $CRON_SECRET
   v
proxy.ts (changed: this one path passes without a session)
   |
   v
app/api/cron/keepalive/route.ts (new)
   |-- header missing or wrong --> 401, no Upstash call
   |
   +-- header matches --> upstashStore().incr("keepalive:kal")
                             |
                             v
                   Upstash kal-login-limiter (shared with star)
                             ^
                             |  rl:login:* keys (unchanged)
app/api/auth/login/route.ts -+  and star's login route (unchanged)
```

## Gate 1 decisions (the owner picks; the tasks below build the recommendation)

1. **Which option. Recommend A, the daily ping.**
   - **A. Daily ping (recommended).** Free, about 40 lines plus two small tests. Daily runs give about 29 missed runs of slack before the 30-day minimum. One ping covers star too, because star uses the same store. The weak spot: if the cron stops (cron disabled, `CRON_SECRET` wrong, Kal project removed), nothing alerts except the cron log and Upstash's warning emails. Those emails go to the Personal Upstash account's address, so that inbox must be one the owner reads.
   - **B. Paid plan (Pay as You Go with a budget).** No code. The owner adds a card to the Personal Upstash account, moves `kal-login-limiter` to Pay as You Go, and sets a budget. The FAQ suggests a paid plan for databases that idle, but it does not say in plain words that paid databases are never archived. Login traffic for one user costs almost nothing. A stranger who spams the login route can still burn commands up to the budget. Then the store is rate limited, and logins fail closed, which is the same state as today's outage. If the owner picks B, the build is only the `STATE.md` gotcha rewrite and the owner's account steps.
   - **C. Fail open (recommended against).** When the store throws, the login route skips the limiter and compares the password. The ticket requires a reason why that is acceptable, and this plan does not find one. Free is capped at 500K commands per month, and every login attempt costs 3 to 5 commands. Upstash does not say what happens to a Free store past the cap. If it refuses commands, a stranger who sends about 100K to 170K login attempts in a month turns the limiter off. With fail open, the attacker then gets unlimited guesses, which is the hole #38 closed. With fail closed, the attacker can only block logins. If the owner picks C anyway, the change is a `try`/`catch` around `limiter.attempt` in `app/api/auth/login/route.ts`, and a test with a store that throws. That file is also on #93's list. See the overlap note below.

2. **`vercel.json` `crons`, not Vercel Schedules.** Vercel now marks Cron Jobs as legacy and says they "will be migrated to Schedules in the future". Schedules is in public beta. One thing Schedules adds is a function target with no public URL, so a stranger could not even reach the route. Cron Jobs are generally available, need no new dependency, and the route code stays the same after a later migration. Pick: `crons` now, and move to Schedules when it leaves beta.

3. **The ping is `INCR keepalive:kal` through the existing `upstashStore()`.** Upstash does not define "activity". A write counts under any definition, and a read might not. `incr` is already on the `RateLimitStore` interface, so the route needs no new store method and `lib/rate-limit.ts` does not change. The key never expires. It is one small counter, and it also shows how many pings landed. The `keepalive:` prefix keeps it apart from `rl:login:*`. A duplicate cron run only adds one to the count, so it is harmless.

4. **The secret compare is constant time.** Vercel's example uses `!==`. The plan hashes both sides with sha256 and uses `timingSafeEqual`, the same as the login password compare from #38. The helper is written in the new route file, not shared, because sharing it would mean editing `app/api/auth/login/route.ts`, which #93 also edits.

5. **Run at 10:00 UTC.** The hour is arbitrary. Any daily hour meets the 30-day rule.

**Overlap with #93 (runs in parallel on port 3103):** with option A or B, this ticket does not change `lib/rate-limit.ts` or `app/api/auth/login/route.ts`. It only imports `upstashStore` from `lib/rate-limit.ts`, and #93 must keep that export, which #93's constraints already require. The two accepts can land in either order. With option C, this ticket edits `app/api/auth/login/route.ts`, which is also on #93's list. Then the owner should land #93 first and rebase this ticket.

**Found while planning, out of scope:** star's limiter uses the same key names (`rl:login:count:<ip>`, `rl:login:block:<ip>`) in the same store. So one IP's failed logins on star and on Kal share one count and one lockout. On accept, the owner picks the repo for a follow-up issue (a per-app key prefix). It is not fixed here.

## Review Focus

1. **`CRON_SECRET` unset in an environment.** The expected header is then `Bearer undefined`, so a stranger who sends exactly that must get 401. Test in Task 1.
2. **The proxy blocks the cron.** Without the exemption, the proxy answers the cookie-less cron request with 401 every day, and the store is archived 30 days later with no visible failure. Test in Task 1 (proxy test).
3. **Too wide an exemption.** A prefix match on `/api/cron` would open any later cron route to strangers. Test in Task 1: `/api/cron/other` without a session gets 401.
4. **A stranger keeps the store awake.** A request without the right secret must not reach Upstash. Test in Task 1: the fake store has no `keepalive:kal` key after a 401.
5. **The secret is set after the deploy.** A deployment keeps the `CRON_SECRET` that it was built with. If the owner sets the secret after the push, every run returns 401 until the next deploy. The accept steps put the secret first.
