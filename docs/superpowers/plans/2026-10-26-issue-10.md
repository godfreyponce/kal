# Real label data for the estimated staples: Issue #10 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Eight foods that run on guessed macros get real numbers, from a package label or USDA. In the live DB they get `is_estimated = false`. The six that are also in the seed get the same numbers in `db/seed-data.ts`, so a reseed does not bring the guesses back.

**Architecture:** One data file, `db/label-data.ts`, holds each food's label facts as printed, plus one pure function, `perBasis()`. That function converts a label serving to the food's existing serving basis, raw to cooked included. The seed file gets the converted numbers as literals, and a test ties them to the label table. A one-off script, `db/apply-label-data.ts`, writes the converted numbers to the live rows by id. It runs as a dry run unless it gets `--apply`. It writes macros, `is_estimated`, `brand`, and `store`, plus one rename (the milk), and nothing else.

**Tech Stack:** TypeScript, Drizzle on Neon (`drizzle-orm/neon-http`, `db.batch` for all-or-nothing writes), vitest, `npx tsx` for the script.

**Spec:** GitHub issue #10 (no design spec in `docs/superpowers/specs/`). The issue had no **Done when**. The owner settled it in the /run-ticket thread on 2026-10-26 and 2026-10-27:

- **Done when:** Each in-scope food has real numbers in the live DB with `is_estimated = false`. `db/seed-data.ts` carries the same numbers for the seed foods, and `db/seed-data.test.ts` is green.
- **Scope:** The 6 seed staples, plus live-only Mozzarella and the milk. Restaurant dishes and the Sushi roll stay estimated. **Ground beef 80/20 and corned beef are deferred to #82**, because the owner will photograph those packages first.
- **No-label foods:** A USDA value counts as real data, which matches #44's rule "Omit for label or lookup data". A raw or dry label converts to cooked with the seed's `rawToCookedYield` (rice 3.0, chicken 0.75).
- **Targets:** This ticket does not write live targets. `computeTargets()` affects only a fresh seed.

## Decisions for gate 1 (most likely to be wrong first)

1. **A script writes the live rows, not the Groceries label card.** The label card is unsafe for weighed foods. `applyLabel()` (`app/groceries/grocery-editor.tsx:175`) sets the serving to the label's grams. `updateGrocery()` (`lib/groceries.ts:163-166`) then rewrites `serving_desc` to `"<n> g"` and does not rescale `meal_items`. The live plan holds chicken ×1.7 and rice ×3 as multipliers of a 100 g basis. A 112 g label would make 1.7 mean 190 g. The script keeps every basis, does the conversion in tested code, and you can rerun it.
2. **Live targets go stale on purpose.** Live targets are 3,712 kcal / 175 P / 400 C / 146 F. The live plan sum is 3,712 / 206 / 400 / 146: kcal, carbs, and fat equal the plan sum, and protein is the owner's 175 floor. A food edit does not run `recomputeTargets()` (`lib/plan.ts:132`). A plan edit does (`replaceMealItems`, `deleteMeal`). After the update, kcal, carbs, and fat lag the new plan sum until the next plan edit. That edit also resets protein from 175 to the plan sum. The dry run prints the plan sum before and after, so the owner sees the size of the jump. The biggest mover is rice, from 130 to 115 kcal per 100 g, at ×3 in two meals.
3. **The milk is renamed** from "Whole milk" to "Horizon Organic 2% milk (DHA)". The owner's carton is 2%, not whole. The row keeps its id, so the plan's Milk meal keeps it. Logged entries keep their snapshotted names and macros.
4. **`store` is set** to the store the owner named: Tom Thumb for eggs, chicken, vegetables, and mozzarella; Costco for rice and oil. Today, three of those say Walmart. The `link` column is not touched, so the old Walmart and Costco links stay.
5. **Chicken uses USDA raw, converted at 0.75.** The Tom Thumb page's per-4-oz line (130 cal, 0.5 g fat, 26 g protein) is not consistent with itself, and its per-100 g box is the USDA entry. The owner picked USDA. If the printed pack label disagrees later, change its row in the table and rerun the script.
6. **Frozen mixed vegetables use the frozen label with yield 1.** Boiling barely changes their weight. The seed's `rawToCookedYield` for this food is `null`, which agrees.

## Review Focus

1. **Raw label put on a cooked food.** Chicken and rice must carry `cookedPerRaw` equal to the seed's `rawToCookedYield` (0.75 and 3.0). Pinned by the Task 1 test `cooked foods convert with the seed's yield`.
2. **Label unit is not grams** (milk in mL, oil per tbsp, eggs per egg). For count foods, `basisG` equals `servingG`, so the scale is 1. Pinned by the Task 1 test `count food keeps the label numbers`.

### Task 2: The live apply script (dry run by default)

**Files:**
- Create: `db/apply-label-data.ts`

**Interfaces:**
- Consumes: `LABEL_FOODS` and `perBasis` from Task 1. Uses `db` from `db/index.ts` and `foods`, `mealItems`, `profile` from `db/schema.ts`. Imports `./env` first, as `db/apply-seed-v2.ts` does.

- [ ] **Step 1: Write the script.** The header comment says what the script writes, gives the run line `npx tsx db/apply-label-data.ts [--apply]`, and warns never to run `db/apply-seed-v2.ts`, because it replaces the live plan and targets. The script does these steps, in order:
  1. Load the live `foods` rows whose ids are in `LABEL_FOODS`. If any id is missing, or its `name` matches neither the entry's `name` nor its `newName`, or its `serving_desc` differs from the table's guard, print each mismatch and exit 1 before any write. Accepting `newName` lets the script rerun after the write. Otherwise print `guard: N/N rows match`.
  2. Print one line per food: `name: <old kcal>/<P>/<C>/<F> (estimated) -> <new kcal>/<P>/<C>/<F>`. Add the rename, brand, and store changes when there are any.
  3. Compute the live plan sum (Σ `meal_items.quantity` × food macros, every meal) twice, in memory: once before and once with the new numbers. Print both, and print the current `profile` targets on the line below. Write nothing.
  4. Only with `--apply`, run one `db.batch([...])` of updates by id. Each update sets `kcal`, `proteinG`, `carbsG`, `fatG` (as strings, the way `updateGrocery` writes them), `isEstimated: false`, and `brand`. It also sets `store` when the entry has one, and `name` when the entry has a `newName`. Print `applied N rows`. Without the flag, print `dry run: nothing written (pass --apply)`.
