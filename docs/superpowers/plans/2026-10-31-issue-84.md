# Interrupted tool turns: Issue #84 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A chat turn that stops between an assistant `tool_use` and its `tool_result` no longer makes every later message in that session fail with a 400. And a client that disconnects mid-turn no longer stops the turn before its results are saved.

**Architecture:** Two small seams, each in its own new lib file with a test. (1) `closeOrphanToolUses()` in `lib/chat-history.ts` is a pure function. It runs on the full message list the route sends: the stored history plus the new user message. It gives each unanswered `tool_use` an in-memory `tool_result` with `is_error: true`, and it writes nothing to the DB. (2) `sseStream()` in `lib/sse-stream.ts` owns the SSE `ReadableStream`. A `cancelled` flag set in the stream's `cancel()` makes `send` a no-op and skips the final `close()`, so the turn runs to the end. `app/api/chat/route.ts` calls both. `lib/chat-turn.ts` does not change.

**Tech Stack:** Next 16.2.9 route handler, `@anthropic-ai/sdk` 0.105.0 types (`MessageParam`, `ToolResultBlockParam`), Node web streams, vitest 4.

**Spec:** GitHub issue #84 and the **Done when** the owner agreed at planning, posted as a comment on the issue (https://github.com/godfreyponce/kal/issues/84#issuecomment-6544893308). No design spec in `docs/superpowers/specs/`. The issue is not labeled `ready-for-agent`; the owner typing `/run-ticket 84` is the green light.

## Decisions for gate 1

The owner picked these at planning (all recommended options): a synthetic `is_error` result kept in memory only (not dropping the message); finish the whole turn after a disconnect (not stopping after the current tools); and the Done when posted as an issue comment.

1. **Repair runs on `[...history, newUserMessage]`, not inside `loadHistory`.** With an orphan at the tail, a repair inside `loadHistory` would have to add a separate user message for the synthetic results, and then the route adds the new user text after it. That gives two user messages in a row, and the history would rely on the API merging them. When the repair runs after the new message is added, the synthetic blocks go to the front of that message's content, which is the position the API requires. It runs again on every load, gives the same output each time, and writes nothing.
2. **`loadHistory` stays in `route.ts`.** At planning I said it would move to `lib/chat-history.ts` so a test could import it. With decision 1, the test covers only the pure function, so moving `loadHistory` buys nothing, and leaving it is the smaller diff. Only the new function goes in the new file.
3. **No `npm run eval`.** The AGENTS.md eval rule covers `lib/system-prompt.ts`, `lib/tools.ts`, `lib/anthropic.ts`, and `lib/chat-turn.ts`. This plan changes none of them. The repair changes model input only for sessions that would get a 400 today.

## Review Focus

1. One assistant message with two `tool_use` blocks and no results gets two synthetic results, one for each id. (Task 1 test.)
2. A partly answered message (the next row has a result for one id of two) keeps the real result and adds a synthetic one only for the missing id. (Task 1 test.)
3. An orphan in the middle of the history, followed by a stored user text, gets its synthetic results ahead of that text in the same message. A result placed after text gets a 400. (Task 1 test.)
4. A clean history comes back deep-equal: a session with no orphan sends exactly what it sends today. (Task 1 test.)
5. A send after the reader has cancelled (the `onToolResult` hook while a tool runs) must not throw, or `runChatTurn` exits before `onToolResults` saves the row. (Task 2 test.)

### Task 1: Repair unanswered tool_use blocks before the request

**Files:**
- Create: `lib/chat-history.ts`
- Test: `lib/chat-history.test.ts`
- Modify: `app/api/chat/route.ts:86` (the `const messages` line)

**Interfaces:**
- Produces: `export const INTERRUPTED_TOOL_RESULT: string` (the verbatim text in Global Constraints) and `export function closeOrphanToolUses(messages: Anthropic.MessageParam[]): Anthropic.MessageParam[]`.

Behavior: for each assistant message that has `tool_use` blocks, find the ids the next message does not answer with a `tool_result` block. If no ids are missing, change nothing. If the next message is a user message, its new content is `[existing tool_result blocks, synthetic blocks for the missing ids, the other blocks]`. If there is no next message, or it is not a user message, insert a new user message that has only the synthetic blocks. Each synthetic block is `{ type: "tool_result", tool_use_id: id, is_error: true, content: INTERRUPTED_TOOL_RESULT }`. A user message with string `content` counts as one text block. Return new message objects, and do not mutate the input.

### Task 2: Keep the turn running after the client disconnects

**Files:**
- Create: `lib/sse-stream.ts`
- Test: `lib/sse-stream.test.ts`
- Modify: `app/api/chat/route.ts:90-139` (the `encoder` line and the `new ReadableStream({...})` block)

**Interfaces:**
- Produces: `export function sseStream(run: (send: (obj: unknown) => void) => Promise<void>): ReadableStream<Uint8Array>`.

Behavior: `start(controller)` calls `run(send)` and closes the controller in `finally`. `send` enqueues `data: ${JSON.stringify(obj)}\n\n`, UTF-8 encoded. The underlying source's `cancel()` sets `cancelled = true`. After that, `send` returns without enqueueing, and `finally` skips `controller.close()`. Receipt: on Node 24.14.1, both `enqueue` and `close` throw `Invalid state: Controller is already closed` after a reader cancels (probed at planning). No test covers the `close` guard, because a throw from `start` after a cancel is swallowed by the stream and nothing can observe it. `run` owns its own try/catch. `sseStream` does not catch errors from `run`.

- [ ] **Step 1: Write the failing tests** in `lib/sse-stream.test.ts`:
  - `streams each sent object as an SSE frame, then closes`: `run` sends `{ type: "a" }` and `{ type: "b" }`. Read the stream to the end and decode it. The text equals `'data: {"type":"a"}\n\ndata: {"type":"b"}\n\n'`.
  - `finishes the run after the reader cancels`: `run` sends `{ type: "model" }`, awaits a gate promise the test controls, sends `{ type: "late" }`, then resolves a `finished` promise. The test reads one chunk, calls `await reader.cancel()`, opens the gate, and then `await expect(finished).resolves.toBeUndefined()`. Today's inline `send` throws on `{ type: "late" }`, so `finished` never resolves.
