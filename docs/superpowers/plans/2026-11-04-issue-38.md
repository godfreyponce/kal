# Rate-limit the login endpoint (#38) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `POST /api/auth/login` refuses an IP with `429` after 5 attempts, with a lockout that doubles each time, and it compares the password in constant time.

**Architecture:** A new `lib/rate-limit.ts` holds a `LoginRateLimiter` that runs on a small `RateLimitStore` interface. At runtime the store is Upstash Redis (`@upstash/redis`). In tests it is an in-memory fake with a clock that the test moves by hand. The route asks the limiter for the attempt **before** it reads the password. Thus a locked IP never reaches the compare, and a parallel burst cannot slip past the count. A committed attacker script, `scripts/redteam/login-guesser.ts`, runs against a local dev server once before the limiter and once after. Both outputs are gate-2 evidence.

**Tech Stack:** Next 16 route handlers, `@upstash/redis` (REST client), `node:crypto` `timingSafeEqual`, Vitest.

**Spec:** Issue #38 (`gh issue view 38`). The issue has no comments and no blocker. No design spec. Read `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md` before you change the route.

## Planner decisions (gate 1, the owner confirms or changes)

1. **This ticket runs through `/run-ticket`, not `/kal-redteam`.** A saved note says that `/kal-redteam` owns red-team issues. That command no longer exists in `~/.claude/commands`. The owner typed `/run-ticket 38`, and the plan takes that as the go-ahead.
2. **Every attempt counts before the compare.** The July draft checked for a lockout, compared the password, and only then counted the failure. Twenty requests sent at once all pass the check before any of them counts, so all twenty get a guess. This plan counts the attempt first with an atomic `INCR`. After the threshold, an attempt gets a guess only if it wins an atomic `SET NX` on the lockout key. A burst therefore gets at most 5 guesses. A correct password clears the count.
3. **The numbers.** Threshold 5 comes from the ticket ("~5"). The other three are planner guesses with no measured basis: the first lockout is 30 s, each later lockout doubles, the cap is 1 h, and the count clears after 24 h with no attempts. The 24 h window is longer than the 1 h cap on purpose. With a shorter window (the draft had 15 min), the count clears during a long lockout, the attacker gets 5 fresh guesses, and the cap has no effect. With these values an attacker gets about 24 guesses a day after the first day.
4. **Fail closed when Upstash is missing or down.** `upstashStore()` throws if `KV_REST_API_URL` or `KV_REST_API_TOKEN` is missing. A Redis error is not caught. Either way, login returns 500 and nobody can log in. Sessions that already exist keep working. The other choice is to fail open (skip the limiter), which leaves the ticket's hole open during an outage.
5. **Env is already in place for prod.** `vercel env ls` shows `KV_REST_API_URL` and `KV_REST_API_TOKEN` on Production, Preview and Development (Upstash came from the Marketplace in July). The values in `~/Developer/kal-redteam/.env.local` are the same store (checked by hash only). Only `~/Developer/Kal/.env.local` is missing them. Task 3 copies the two lines across. No Vercel step, and no `vercel env pull`. Local and prod share one Redis. Local keys hold loopback IPs, so they never touch a real client's count.
6. **The login page does not change.** During a lockout, the page still shows "Incorrect password", because it shows that text for any non-OK reply (`app/login/page.tsx:47`). That is misleading, but it is a UI change, outside the ticket. On accept, file a follow-up issue: "login page says Too many attempts on a 429".
7. **Per-IP only.** An attacker with an IPv6 /64 block or many hosts can spread guesses across IPs. The ticket asks for a per-IP limiter. On accept, file a follow-up red-team issue for a global limit or /64 buckets.
8. **The route test mocks two modules with `vi.mock`.** This is the first `vi.mock` in the repo. It swaps `upstashStore` for the fake store and `getSession` for a stub, because `cookies()` throws outside a real request. The other choice is a route test against the live Upstash store. The plan does not take it, because then every `npm test` run would need the KV keys and would write to the store that prod uses. The guesser's "after" run against the real store is the live proof.
9. **The guesser output is not committed as a file.** It is pasted at gate 2, and the accept-time `docs/HISTORY.md` section quotes the two summary blocks.

## Review Focus

1. **Passwords of a different length.** `timingSafeEqual` throws `RangeError` on buffers of unequal length. Without the sha256 step, a short guess returns 500, not 401. Task 3 test: a 1-char and a 200-char wrong password both get 401.
2. **A parallel burst from one IP.** Twenty attempts at once must give at most 5 guesses. Task 2 test, with `Promise.all`.
3. **A correct password during a lockout.** It must get 429, not log in, or the lockout gives the attacker nothing. Task 3 test.
4. **Upstash env missing.** `upstashStore()` must throw and not return a store that does nothing. Task 2 test.
5. **No `x-forwarded-for` header.** All such requests share the `"unknown"` bucket. On Vercel the header is always set and Vercel overwrites the client's value ("we currently overwrite the X-Forwarded-For header and do not forward external IPs. This restriction is in place to prevent IP spoofing", Vercel request-headers docs). Task 2 `clientIp` tests.

### Task 2: The limiter module

**Interfaces:**
- Produces, in `lib/rate-limit.ts`:
  ```ts
  export interface RateLimitStore {
    pttl(key: string): Promise<number>;            // ms left; <= 0 when no live key
    incr(key: string): Promise<number>;
    pexpire(key: string, ms: number): Promise<unknown>;
    set(key: string, value: string, opts: { px: number; nx: true }): Promise<unknown>; // "OK" if set, null if the key exists
    del(...keys: string[]): Promise<unknown>;
  }
  export interface RateLimitConfig { threshold: number; windowMs: number; baseBackoffMs: number; maxBackoffMs: number }
  export const LOGIN_RATE_LIMIT: RateLimitConfig = { threshold: 5, windowMs: 24 * 60 * 60_000, baseBackoffMs: 30_000, maxBackoffMs: 60 * 60_000 };
  export type AttemptVerdict = { allowed: true } | { allowed: false; retryAfterMs: number };
  export class LoginRateLimiter {
    constructor(store: RateLimitStore, cfg?: RateLimitConfig); // cfg defaults to LOGIN_RATE_LIMIT
    attempt(id: string): Promise<AttemptVerdict>;
    reset(id: string): Promise<void>;
  }
  export function upstashStore(): RateLimitStore; // KV_REST_API_URL + KV_REST_API_TOKEN, throws if either is missing
  export function clientIp(headers: Headers): string; // first x-forwarded-for hop, then x-real-ip, then "unknown"
  ```
- Produces, in `lib/rate-limit-fake-store.ts`: `export function fakeStore(clock: { now: number }): RateLimitStore`. It holds values and expiry times in Maps. A key is dead once `expiry <= clock.now`. `set` with `nx` returns `null` when the key is alive, and `"OK"` when it sets the key. `pttl` returns `-2` for a dead key. Base it on the draft's `memStore`, with `nx` added.

- [ ] **Step 1: Write the failing tests** in `lib/rate-limit.test.ts`. Use the TEST-NET-3 IPs `203.0.113.x`, a new one for each test, and `LOGIN_RATE_LIMIT` as the config.
  - `allows 5 attempts from one IP and blocks the 6th`: 5 times `attempt(ip)` gives `{ allowed: true }`. The 6th gives `{ allowed: false, retryAfterMs: 30_000 }`.
  - `after a lockout ends, allows one attempt and doubles the next lockout`: after the 6th is blocked, add 30_000 to `clock.now`. Then `attempt` → allowed, and the next one → `retryAfterMs: 60_000`. Add 60_000. Then allowed, and the next → `120_000`.
  - `caps the lockout at maxBackoffMs`: loop 15 times. Each time, add the last `retryAfterMs` to `clock.now`, make one allowed attempt, and then one blocked attempt. Every `retryAfterMs` is `<= 3_600_000`, and the last one is `=== 3_600_000`.
  - `a parallel burst from one IP gets at most 5 attempts through`: `await Promise.all` of 20 `attempt(ip)` calls. Exactly 5 are allowed.
  - `one IP's lockout does not block another IP`.
  - `reset clears the count and an active lockout`: 6 attempts (the 6th is blocked), then `reset`. The next 5 are allowed and the 6th is blocked.
  - `the count starts over after windowMs with no attempts`: 4 attempts, then add `windowMs` to `clock.now`. The next 5 are allowed and the 6th is blocked.
  - `upstashStore throws when the KV env is missing`: `vi.stubEnv("KV_REST_API_URL", undefined)` → `expect(() => upstashStore()).toThrow()`. Call `vi.unstubAllEnvs()` in `afterEach`.
  - `clientIp`: `"198.51.100.4, 10.0.0.1"` → `"198.51.100.4"`. `" 198.51.100.5 "` → `"198.51.100.5"`. Only `x-real-ip: 198.51.100.9` → `"198.51.100.9"`. No headers → `"unknown"`.

- [ ] **Step 4: Implement `lib/rate-limit.ts`.** Keys: `rl:login:count:<id>` and `rl:login:block:<id>`. `attempt` must follow this order, because the order is what closes the burst race:
  ```
  ttl = pttl(block); if ttl > 0 → { allowed: false, retryAfterMs: ttl }
  n = incr(count); pexpire(count, windowMs)          // refresh the window on each counted attempt
  if n < threshold → { allowed: true }
  backoff = min(baseBackoffMs * 2 ** (n - threshold), maxBackoffMs)
  if set(block, "1", { px: backoff, nx: true }) is truthy → { allowed: true }   // this attempt is the one guess the lockout allows
  ttl = pttl(block); → { allowed: false, retryAfterMs: ttl > 0 ? ttl : backoff }
  ```
  `reset` deletes both keys in one `del`. `upstashStore` returns `new Redis({ url, token })` and does not cast it. If `tsc` rejects the structural match, narrow the interface. Do not use `as unknown as`. Use comments only for the why: Upstash for durability across serverless instances, and the attempt order.
