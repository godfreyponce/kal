# Login limit across many IPs (#93) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A guesser who rotates IP addresses gets a bounded number of login guesses per day in total, and the owner can still log in from a network they have used before.

**Architecture:** `lib/rate-limit.ts` keeps its per-IP counter as it is. `LoginRateLimiter` gets a second counter of the same kind with one shared key: the global count. An attempt first passes the per-IP count. Then, if the IP has no "owner pass" (a key set by an earlier correct password from that IP), it must also pass the global count. A correct password clears the per-IP keys, as now, and sets the owner pass. The route (`app/api/auth/login/route.ts`) does not change: it still calls `attempt(ip)` and `reset(ip)`. So star (#33 in `godfreyponce/star`) can port this by copying `lib/rate-limit.ts` byte for byte.

**Tech Stack:** `@upstash/redis` behind the existing `RateLimitStore` interface, Vitest with the existing fake store.

**Spec:** Issue #93 (`gh issue view 93`). No comments, no blocker, no design spec. Background: plan `docs/superpowers/plans/2026-11-04-issue-38.md` (decisions 2, 3, 7).

## Data flow

```text

   |
   v

   |
   +-- 1. per-IP count ---------------> Upstash  rl:login:count:<ip>, rl:login:block:<ip>
   |      refused --> 429
   +-- 2. owner pass? (new, read) ----> Upstash  rl:login:known:<ip>  (new)
   |      yes --> allowed, global count skipped
   +-- 3. global count (new) ---------> Upstash  rl:login:global:count:all,
   |      refused --> 429                         rl:login:global:block:all  (new)
   v
password compare
   |  right
   v
LoginRateLimiter.reset(ip)  (changed)
   +-- delete per-IP keys ------------> Upstash  rl:login:count:<ip>, rl:login:block:<ip>
   +-- set owner pass (new) ----------> Upstash  rl:login:known:<ip>  (new, 30 d TTL)

```

## Planner decisions (gate 1, the owner confirms or changes)

1. **Which fix: a global limit with an owner pass. No /64 buckets for now.** The four options in the ticket:
   - **Accept the risk.** No code. Today an attacker gets about 24 guesses a day for each IP after the first day (#38 plan, decision 3). With 1,000 proxy IPs, that is about 24,000 a day. Whether that is safe depends only on how strong `APP_PASSWORD` is.
   - **/64 buckets for IPv6.** This groups IPv6 addresses by their first 64 bits. It closes the worst case, because one /64 holds 2^64 addresses. But prod does not take IPv6 today: `dig AAAA kal-delta.vercel.app` returned no record on 2026-11-11 (only the two A records). It does nothing against many IPv4 hosts. A free tunnel /48 still holds 65,536 /64s.
   - **Global limit.** One count for all IPs. The total is bounded no matter how many IPs the attacker has: after the global threshold, about one guess an hour for the whole internet. The cost: an attacker can trip it and block the owner's new logins too. Decision 3 covers that.
   - **Both.** The global limit already bounds IPv6 rotation in the same way that it bounds IPv4 rotation. So /64 buckets would add almost nothing while prod is IPv4-only.
   Pick: the global limit. If the owner picks "both", do Task 3 too. It is written out below and is skipped by default.
2. **The global numbers.** `GLOBAL_LOGIN_RATE_LIMIT = { threshold: 20, windowMs: 24 h, baseBackoffMs: 30 s, maxBackoffMs: 1 h }`. The threshold of 20 is a guess: four times the per-IP threshold, with no traffic data behind it. The other three values copy `LOGIN_RATE_LIMIT`, for the same reason as in #38 (the window must outlast the cap). Under a steady attack, all IPs together get about 20 + 24 guesses on the first day and about 24 a day after that.
3. **How the global limit does not lock the owner out: the owner pass.** A correct password sets `rl:login:known:<ip>` for 30 days. An IP with that key skips the global count, but it still has its own per-IP count. 30 days is a guess, chosen to outlast two sessions: a session lasts 14 days (iron-session 8.0.4 default `ttl`, and `lib/session.ts` sets no `ttl`). Each correct password renews the key, so a network the owner uses at least once a month keeps its pass. What is left: during an attack, the owner on a **new** network (a hotel, a new phone IP) gets 429 with a `Retry-After` of up to 1 h. Sessions that already exist keep working. Phone carriers often change the IPv4 address, so a phone login is the case most likely to have no pass. The other choice is no owner pass, which is less code but lets an attacker block every new login.
4. **The per-IP count runs first, and only an attempt that the per-IP count allows reaches the global count.** So one noisy IP spends at most its own ~24 a day of the global count. It cannot use up the global count by itself. An attempt that the global count refuses has already counted against its IP. That is the safe direction.
5. **A correct password does not clear the global count.** Only the owner can send a correct password, so clearing it would cost the attacker nothing. But it would also reset the attacker's backoff and give them 20 fresh guesses.
6. **Key names, and star shares them.** The per-IP keys keep their names (`rl:login:count:<ip>`, `rl:login:block:<ip>`), so live keys and star's current copy stay valid. The global counter uses the prefix `rl:login:global` with the id `all`, so no IP string can name a global key. Star uses the same store and the same `rl:login:*` keys (star #30 plan, "shared"). After star #33 copies the file, the two apps share one global count and one owner pass for each IP. That fits one owner with two doors: an attack on star also limits new Kal logins from networks with no pass. The other choice is a per-app prefix. It needs a constructor argument, and then the file is no longer a byte copy. Not taken.
7. **`lib/rate-limit.ts` changes.** #94 runs at the same time and may change this file too. The owner orders the two accepts. This plan changes the `LoginRateLimiter` class and adds two exports near `LOGIN_RATE_LIMIT`. It does not touch `upstashStore()` or `clientIp()`. Whichever ticket lands second rebases onto the other.
8. **The store interface does not change** (ticket constraint). The owner pass uses `pttl` to read and `del` + `set(nx)` to renew. Fail closed does not change: any store error still throws, and login returns 500.
9. **The guesser gets a rotation mode, and its runs write to the live store.** `ROTATE=1` sends a different `x-forwarded-for` on each attempt, from `198.51.100.0/24` (TEST-NET-2, RFC 5737: a documentation range, never a real client). The dev server's `.env.local` points at the same Upstash store that prod and star use. So the "after" run sets the global keys there, and they would block new prod logins with no owner pass for up to a day. Task 4 deletes every key the runs made, and checks that they are gone. `next dev` must pass the header through. If the "before" run gets a 429 at attempt 6, the header is not passed through. Then Task 1 stops and reports.
10. **The route test gets a new store for each test.** `lib/login-route.test.ts` shares one fake store across all its tests and gives each test its own IP. With a global count, those tests now add up: they make 19 global attempts today, one below the threshold. One more test would trip it, and an unrelated test would then fail. A `beforeEach` that makes a new store removes that link (the same fix as star #30 plan, decision 6).
11. **This ticket runs through `/run-ticket`, not `/kal-redteam`.** It has the `red-team` label. A saved note says that `/kal-redteam` owns red-team issues, but that command no longer exists (#38 plan, decision 1). The owner typed `/run-ticket 93`.
