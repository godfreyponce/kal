# Chat tool-call evals: Issue #41 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `npm run eval` runs a fixed set of chat cases against the real Anthropic API on both `CHAT_MODEL` and `FALLBACK_CHAT_MODEL`, with stubbed tools, and prints per-case pass/fail per model, a score, and the run's token cost. It scores the tool calls the model makes, never its wording.

**Architecture:** Two seams come out of the live chat path so the eval drives the real code, not a copy. `renderSystemPrompt(date, ctx)` is the pure half of `assembleSystemPrompt`. `runChatTurn()` in a new `lib/chat-turn.ts` is the tool loop that `app/api/chat/route.ts` runs today, with an injectable `runTool` and hooks for streaming, persisting, and the spend ledger. The route keeps its DB and SSE work in hooks. The eval passes a stub `runTool` and records nothing to `api_calls`. Everything eval-only lives in `evals/`: a synthetic fixture, stateful tool stubs, a pure scorer, the cases, and the runner.

**Tech Stack:** Next 16.2.9, `@anthropic-ai/sdk` 0.105.0 (types `thinking: { type: "adaptive" }` and `output_config: { effort: "low" }`), drizzle row types, vitest 4, `npx tsx`.

**Spec:** GitHub issue #41 (no design spec in `docs/superpowers/specs/`). The issue is not labeled `ready-for-agent`; the owner typing `/run-ticket 41` is the green light.

## Decisions for gate 1

1. **The #59 case uses a structural proxy.** The ticket says "the model subtracts macros itself instead of using tool results", and prose is never scored. Today no write tool returns `remaining`, so the only structural sign of "used the tool" is a `get_day_summary` call after the turn's last `log_food`. That is the case. When #59 lands, write tools return `remaining` and this proxy goes stale. #59 already says "add as an eval case when #41 lands", so its build rewrites this case. Rejected: scoring the remaining-kcal number in the reply text. That scores prose.
2. **Only #40 is known-fail.** #57 and #59 are still open, so their cases may fail today. That is the measurement, and the ticket marks only #40. The `search_foods` stub copies today's phrase match (`ilike '%q%'`), so "cooked white rice" misses "White rice, cooked", the same as live. The build of #57 must change the stub when it changes the real search. Task 5 adds a comment to #57 that says this.
3. **The whole tool loop moves to `lib/chat-turn.ts`, not just a tool-runner parameter.** The ticket allows "a seam for an injectable tool runner". A narrower seam would make the eval copy the loop: the rolling cache mark, the model params, the iteration cap, and the tool_result feed-back. A copy can drift from the route, and then the eval measures nothing. So the route's loop becomes `runChatTurn()`, and the route passes hooks. The model params (`max_tokens`, adaptive thinking, low effort) move into that module, so both callers send the same params. The AGENTS.md gate-2 line names `lib/chat-turn.ts` together with the ticket's three files.
4. **The eval builds its own `new Anthropic()` client.** `lib/anthropic-client.ts` imports `server-only`, and that import throws under plain `tsx` (the #80 decision). The client object holds no prompt and no params, so building it in the runner copies nothing that the ticket protects.
5. **The prompt is built again before each turn, from the stub state.** The route runs `assembleSystemPrompt` again on each request. So the eval also renders the prompt again before each turn, with the stub's current day summary, meal statuses, memory facts, and overrides. Without this, in the two-turn cases the TODAY line says 0 consumed while `get_day_summary` says 450.
6. **Exit code 0 when cases fail.** The ticket forbids a pass threshold with no data behind it. The run exits 1 only when it cannot run: no API key, or a bad `--repeat`.

## Global Constraints

- Score structure (tool names, arguments, numbers), never wording.
- Drive the same system prompt builder, `TOOLS` definitions, and model params that `/api/chat` uses. Do not copy them.
- Never in the commit hook (`.claude/hooks/test-gate.sh`). The eval is not a `*.test.ts` file, and `npm test` never runs it.
- Running it needs a real `ANTHROPIC_API_KEY` in `.env.local` (currently `""`). The owner sets it; the build does not.
- Public repo: fixtures are synthetic. No real profile, plan numbers, or memory facts.
- No baked-in repeat count, cost cap, or pass threshold. `--repeat` defaults to 1 because the ticket says "once per model by default".
- Eval calls write no `api_calls` rows. The eval never calls `recordApiCall`, and it points `DATABASE_URL` at `db.invalid`, so an import that reaches the DB by mistake fails and writes nothing.
- No new dependency.
- Commit format (AGENTS.md `# Commit format`): `type(scope): summary (refs #N)`. Trailers: the harness default `Co-Authored-By` line, nothing else.
- Multi-task plan: build on the existing `issue-41` branch, one commit per approved task. Commits run the test-gate hook, so `npx tsc --noEmit` and `npm test` must be green at each one.
- Verification scope: while iterating, run only the touched test files. Run one vitest at a time across all worktrees.

## Prerequisite

This worktree has no `node_modules`. Run `npm ci` once before Task 1. `.env.local` is present.

## Review Focus

1. **The route's SSE stream must not change.** The client depends on this event order: `model`, then for each tool a `tool_use` before the tool runs and a `tool_result` after it, then `error` ("Reached tool-iteration limit.") only when the cap is hit, then `usage`, then `done`. A thrown error must still give one `error` event and close the stream. There is no route test, and the local key is empty, so the reviewer checks this in the Task 2 diff. Task 2's tests cover the loop under the route.
2. **An API error in one case must not stop the run.** For example, a 400 on turn 2 that comes from history handling. That run is a FAIL with the error message, and the other cases continue. Test: `scoreCase` with an `error` fails with `error: <msg>` (Task 3), and the runner wraps each run in try/catch (Task 5).
3. **A model that sends numbers as strings** (`"grams": "113"`) must fail a number check. The real `runTool` ignores non-number values (`num()`), so this is a real failure. Test in Task 3.
4. **No key means no calls.** `npm run eval` with `ANTHROPIC_API_KEY=""` prints one line and exits 1 before it builds a client. Verified by hand in Task 5.
5. **The stubs must not import the DB.** `evals/stubs.ts` uses only pure modules (`lib/resolve-item`, `lib/units`) and type-only imports. Task 4's test imports it with no `db/env`. If the stubs reached `db/index.ts`, the test would throw "DATABASE_URL is not set" or go to the network.

### Task 3: The scorer

**Files:**
- Create: `evals/score.ts`
- Test: `evals/score.test.ts` (pure; no DB, no env)

**Interfaces:**
- Produces:
  ```ts
  export type ArgCheck = string | number | boolean | readonly [min: number, max: number] | ((value: unknown) => boolean);
  export type CallSpec = { tool: string; args?: Record<string, ArgCheck>; turn?: number; label?: string };
  export type RecordedCall = { turn: number; tool: string; input: Record<string, unknown> };
  export type Expectations = { must: CallSpec[]; mustNot: CallSpec[]; ordered?: boolean };
  export function matchesCall(call: RecordedCall, spec: CallSpec): boolean;
  export function scoreCase(calls: RecordedCall[], exp: Expectations, error?: string): { pass: boolean; failures: string[] };
  ```
  Turns are 0-based. A spec with no `turn` matches any turn. `failures` lines read `missing: <label ?? tool + JSON args>`, `forbidden: <tool> <JSON input>`, and `error: <msg>`.

- [ ] **Step 1: Write the failing tests** in `evals/score.test.ts`:
  - `matchesCall`: exact string, number, and boolean checks. The range `[110, 116]` matches 113, 110, and 116, and does not match 117 or `"113"` (a number check needs `typeof === "number"`). A predicate gets `undefined` for a missing arg. A check on a missing arg fails. `turn: 1` does not match a call on turn 0.
  - `scoreCase` unordered: specs `[{tool:"log_food"}, {tool:"log_food", args:{food_id:2}}]` and calls `[log_food{food_id:2}, log_food{food_id:1}]` give a pass. This is a distinct-call assignment, so a greedy match that takes the food_id 2 call for the first spec would fail it. One `log_food` call for two `log_food` specs fails with one `missing:`.
  - `scoreCase` ordered: specs A then B pass on calls `[A, x, B]` and fail on `[B, A]`.
  - Extra calls that match no spec, for example `get_day_summary`, do not fail a case.
  - A call that matches a `mustNot` spec fails with `forbidden: …`.
  - `scoreCase([], {must:[], mustNot:[]}, "400 bad request")` gives `{ pass: false, failures: ["error: 400 bad request"] }`.

Run: `npx vitest run evals/score.test.ts`

- [ ] **Step 3: Implement `evals/score.ts`.** Unordered `must`: search by backtracking for an assignment of distinct calls to specs (cases are small). Ordered `must`: the specs match an increasing subsequence of calls; the earliest-match greedy search is enough for this.
